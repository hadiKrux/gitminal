# Gitminal Project Architecture

Last updated: 2026-10-27
Scope: Enforced file, folder, layering, and OpenTUI component rules for the Gitminal v1 implementation.
Visual reference: [`gitminal.png`](gitminal.png). The mockup is the authoritative UI target. Every UI feature must match the area of the mockup mapped to it in section 15.

This document is the single architecture contract for the project. It decides where code lives, how layers depend on each other, which OpenTUI component each concern uses, and which paths each feature owns. Behavior is described by each feature's JSDoc and tests, and section 15 records feature ownership. There are no separate feature or specification documents.

## 1. Tech stack (fixed for v1)

| Concern | Choice | Version source |
| --- | --- | --- |
| Runtime | Bun | `>=1.3.14` (`package.json` engines), the floor required by the installed OpenTUI |
| Language | TypeScript, strict, `resolveJsonModule` | `tsconfig.json` |
| Package | `@im4all/gitminal`, version `1.3.0` | `package.json` `name` and `version`; the splash reads both |
| UI | React 19 with `@opentui/react` | `package.json` |
| Terminal rendering | `@opentui/core` | `package.json` |
| Syntax grammars | Vendored tree-sitter wasm plus highlight queries under `assets/parsers`, alongside the parsers bundled with OpenTUI | Generated by `bun run parsers:vendor` from exact devDependencies in `package.json` |
| Entry module | `src/index.tsx`, bundled to `dist/index.js` | `package.json` bin and build script |
| Git access | System git CLI, argument arrays, no shell | Section 10 of this document |
| Tests | `bun test` | This document |

Supported git minimum: **Git >= 2.31.0**. The fixture floor and the integration skip threshold are both 2.31, and every command the app runs is available there. The narrowest requirements are `git branch --show-current` (2.22), the unambiguous upstream atoms `%(upstream:remotename)` and `%(upstream:remoteref)` (2.28), and `git log --diff-merges=<mode>` (2.31), so 2.31 is the safe floor rather than a version the app happens to be tested on.

No other runtime dependency is added without updating this document. No UI toolkit, state library, router, or HTTP client is introduced. The startup update check uses the runtime's global `fetch` and adds no dependency.

## 2. Architectural principles

1. Observable-first, incremental. Every slice must be runnable and inspectable before it grows. The shell and a single working panel land before git breadth.
2. Layered and one-directional. Dependencies point inward: `features -> ui/app -> domain -> lib`. Domain never imports React or OpenTUI.
3. One source of truth per concern. Repository state comes from git, config comes from the config loader, keybindings come from the keymap resolver, colors come from the theme resolver. Features do not keep parallel copies of these.
4. Commands are the only mutation path. UI dispatches command requests to a single command runner; the domain runner only executes them and returns a result; the app-layer command orchestrator applies refresh, status, console, and error effects. No component calls git directly, and no domain module touches a provider or a React hook.
5. One mutation at a time. The command runner serializes writes and returns a blocked result with a visible reason when a second mutation is requested.
6. One handler per action per scope. Action handlers are registered with an explicit scope and target policy, never flat by action ID for a component lifetime. The palette dispatches commands with an explicit target, never to a hidden surface's stale cursor.
7. Explicit states. Every async surface has loading, empty, error, and disabled states with text markers, not color alone.
8. Composition over new renderables. Only existing OpenTUI components and React composition are used. A new renderable requires a documented reason in this file. The one sanctioned registration is OpenTUI's own `FrameBufferRenderable`, registered through `extend` for `ProgressBar`, because the built-in React catalogue has no frame-buffer binding.
9. Match the visual reference. The mockup at `gitminal.png` is the authoritative target for layout, hierarchy, spacing, and density. Behavior comes from each feature's tests and JSDoc; arrangement comes from the mockup. Where the mockup shows a detail the sanctioned OpenTUI component cannot render, this document records the deliberate deviation; the unified `<diff>` one-gutter decision in section 6 is the only v1 deviation.

## 3. Layer model and dependency direction

```text
src/index.tsx            bootstrap only (renderer + root)
   |
   v
src/app/**               providers, hooks, composition root
   |         \             \
   v          v             v
src/features/**   src/ui/**   src/theme/**   feature UI, UI primitives, tokens and icons
   |         \        |          |
   v          v       v          v
src/domain/**     (ui composes ui primitives and theme; theme reads only domain theme and lib)
   |
   v
src/lib/**               pure utilities, no React, no git
```

Allowed imports:

- `src/lib/**` imports only `src/lib/**`.
- `src/domain/**` imports `src/domain/**` and `src/lib/**`. Never React, never a React hook, never `@opentui/*`, never `src/features/**`, never `src/app/**`.
- `src/ui/**` imports `src/ui/**`, `src/lib/**`, and `src/theme/**` (tokens, context, and icons) and React and `@opentui/*`. UI primitives compose other UI primitives. It does not import `src/domain/**`, `src/features/**`, or `src/app/**`.
- `src/features/**` imports `src/ui/**`, `src/app/hooks/**`, provider hooks under `src/app/providers/**`, `src/domain/**`, `src/lib/**`, `src/theme/**`, React, and `@opentui/*`.
- `src/theme/**` imports React, `@opentui/*`, `src/theme/**`, any module under `src/domain/theme/**`, and `src/lib/**`. Type-only use of the domain theme modules is the review norm for token types. It does not import `src/ui/**`, `src/features/**`, `src/app/**`, or a domain module outside `src/domain/theme/**`.
- `src/app/**` imports everything except the test-only imports: the test runners `bun:test` and `node:test`, and the harness under `src/test/**`. No production module imports any of them; only colocated `*.test.*` files and modules already under `src/test/` may.
- Feature to feature imports are forbidden. Cross-feature coordination goes through a provider, a domain command, or a selector exported from `src/domain/**`.
- `src/app/AppShellHost.tsx` is the composition root. It is the only module that imports `features/shell` together with the feature panels, graph, composer, details, diff, console, and overlays. `features/shell/AppShell.tsx` owns layout, region frames, and the shell's own UI, but it receives feature surfaces as `ReactNode` props or children and never imports another feature. Today the quit handler aborts the in-flight command and tears down without a draft prompt; when draft-based quit lands it will read `hasUnsavedDraft` from `DraftProvider`, never from the composer feature.

Forbidden imports and key access (enforced by the section 12 scripts):

- Process spawning (`node:child_process`, `Bun.spawn`, `Bun.spawnSync`, `Bun.shell`, or `Bun.$`) outside `src/domain/git/git.client.ts` and `src/test/git.fixture.ts`.
- Network access (`fetch`, `Bun.fetch`, `globalThis.fetch`, `window.fetch`, `Bun.connect`, `WebSocket`, or a `node:http`, `node:https`, `node:http2`, `node:net`, `node:dgram`, `node:tls`, or `undici` import) outside `src/domain/update/update.check.ts`.
- Hex color literals outside `src/domain/theme/theme.catppuccin.ts`.
- Raw key string comparisons outside `src/domain/keymap/**` and `src/app/hooks/useHotkeys.ts`. `src/app/quit.key.ts` is the only exception: `SplashGate` runs before any provider mounts and compares only the fixed `Ctrl+C` quit chord (`key.ctrl` plus `key.name`) through that single helper. After dismissal the shell's `app.quit` action owns quit through the keymap. The boundary check flags equality comparisons between a string literal and a key-like `name`, `sequence`, `raw`, or `code` access, and allows only those three paths.
- Any external package import inside `src/domain/**` or `src/lib/**`, including React and `@opentui/*`. Node builtins are limited to this per-module allowlist; every other builtin is rejected under domain and lib:

  | Module | Allowed Node builtins |
  | --- | --- |
  | `src/domain/git/git.client.ts` | `node:child_process`, `node:path` |
  | `src/domain/git/git.diff.ts` | `node:fs/promises`, `node:path` |
  | `src/domain/git/git.watcher.ts` | `node:fs`, `node:fs/promises`, `node:path` |
  | `src/domain/config/**` | `node:fs`, `node:fs/promises`, `node:path`, `node:os` |
  | `src/lib/paths.ts` | `node:path`, `node:os` |

  `src/test/**` is test-only. It has no layer import rule of its own, so this builtin allowlist does not apply there. Every module under `src/test/**` remains subject to the spawn and network checks, and `src/test/git.fixture.ts` is the documented spawn exception.

- Non-ASCII or box-drawing glyph literals outside `src/theme/icons.ts`, other than ordinary UI text; every reusable marker must also come from `ICONS`. The catalog holds the sanctioned non-ASCII set only: the push and pull arrows, the expanded and collapsed triangles, the success check mark, and the commit graph's two commit symbols plus its box-drawing line set.

Rules for this tree:

- Folders are kebab-case, singular, and match the feature name.

- `src/test/` holds test-only harness code. `git.fixture.ts` creates, seeds, and removes temporary repositories for integration tests; no production module imports it, and the boundary check rejects a `src/test/**` import outside a colocated test file or another `src/test/**` module.
- `scripts/` holds the section 12 developer checks only. It is tooling, not a feature folder, so the feature naming rule does not apply.
- `AppShellHost.tsx` is the composition root. Feature components never import one another; they receive cross-feature data through providers, commands, or selectors.

Remote rows are one line: the branch name only beneath its remote group header, plus an inline stale or unknown marker, with no commit summary or date line. Row identities and command targets remain remote-qualified, and search results/details retain remote prefixes for cross-group disambiguation. The graph, right-pane, and diff surfaces are not sidebar panels: each owns its `Panel` frame, region id, and scroll container, and `MainArea` only sizes the three regions.

## 5. File naming rules

Enforced:

- React components: `PascalCase.tsx`, one exported component per file, file name equals the exported component name.
- Hooks: `useThing.ts` or `useThing.tsx`, file name equals the exported hook.
- Types only: `<name>.types.ts`. Constants only: `<name>.constants.ts`. Pure logic: `<name>.ts` matching the primary export. Raw-key predicates: `<name>.key.ts` for a pure predicate in the documented pre-shell key path; `src/app/quit.key.ts` is the only current file.
- Value-derived aliases and catalogue-describing interfaces may stay beside the runtime value they describe, because splitting them would make the type and its source drift apart. These are the only named type exports allowed in a runtime module: `ActionId` in `keymap.defaults.ts`, `ThemeToken` and `ThemeTokenTarget` in `theme.tokens.ts`, and `IconName` in `icons.ts`. Every other feature-owned named type or interface belongs in the sibling `*.types.ts` file.
- Tests: colocated `*.test.ts` or `*.test.tsx` next to the file under test. No separate `__tests__` tree. Matching `AGENTS.md`, test files are exempt from the JSDoc, one-exported-component-per-file, component-constants, and function-size split guidance; test helpers and fixtures may stay inline and undocumented.
- No `index.ts` barrels. Import from the exact module path. This keeps dependency edges visible and prevents cycles.
- No file is named `utils.ts`, `helpers.ts`, `common.ts`, or `misc.ts`. Name the concern.
- Path aliases: `@/*` maps to `src/*`. Use `@/domain/...`, `@/ui/...`, `@/features/...`. Relative imports are allowed only within the same folder. One documented exception: `src/app/app.constants.ts` and its colocated test import the root manifest as `../../package.json`, because the app version and package name must have a single source and the manifest sits outside `src`. These are the only cross-folder relative imports; every other import uses `@/*`.

Required `tsconfig.json` addition:

```json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": { "@/*": ["./src/*"] }
  }
}
```

### 5.1 Code documentation and function size

Enforced:

- Every function, class method, and exported arrow function has a standard JSDoc block that states what it does, its parameters, and its return value. Use `@param` and `@returns` tags. A one-line `/** ... */` is acceptable only for a trivial, self-evident helper. Colocated `*.test.ts` and `*.test.tsx` files are exempt from this requirement, and their helpers may stay undocumented.
- Non-obvious behavior, side effects, error cases, and invariants are documented in the JSDoc, not only in the implementation.
- React components are documented with JSDoc on the component function, describing the props and the rendered behavior.
- If a production function becomes big, split it. The target is a function that does one thing and reads top to bottom without deep nesting. Split a function that mixes data preparation with side effects, that nests more than three control-flow levels, or that fallow flags for complexity or size. The old "about 40 lines" rule is a review prompt, not a CI parser. Extract named helpers in the same module or the owning folder rather than growing the function.
- A hook follows the same rule. If a hook grows past a single concern, split it into a hook plus pure helpers in `@/lib` or `@/domain`, or into smaller hooks composed together.
- Pure logic that a JSDoc would otherwise duplicate belongs in `@/domain` or `@/lib` with its own tests, not inline in a component.
- Test files are exempt from the JSDoc, one-exported-component-per-file, component-constants, and function-size split guidance in this document, matching `AGENTS.md`. Test helpers and fixtures may stay inline and undocumented.

Component rules:

1. Keyboard ownership is centralized. `useHotkeys` is the only `useKeyboard` caller after the shell mounts. `SplashGate` runs before the providers mount and is the documented exception while the splash is visible. It owns dismissal and quit, then unmounts as the shell's `useHotkeys` and `app.quit` path takes over. `useHotkeys` resolves precedence (open overlay, then text input, then native list widget, then focused region context, then global), and it calls `preventDefault()` only when it handles the key. Features register handlers by action ID through `useAction`. No feature inspects `KeyEvent` directly.
2. OpenTUI native focus is the single focus authority. The renderer's `currentFocusedRenderable` receives keys. `FocusProvider` is a projection: it derives `activeRegion` from the focused renderable's nearest ancestor region frame, derives `textInputFocused` from `currentFocusedEditor`, and stores `previousRegion` plus the per-region cursor map. It does not hold a competing writable `activeRegion`. Every region frame is a focusable `<box>` with a stable id and `focusedBorderColor`, so the border follows native focus, including when a descendant text input is focused. The focused frame switches its border to the focus token and its title to the text token; the title text itself never changes, so no marker is added to a boxed title. List rows and controls keep their own text markers, except the graph rows, which suppress the selection marker so the lane prefix is the only leading glyph and the dark selected fill identifies the cursor row, and the diff file rows and section headers, which suppress it so the expansion triangle is the only leading glyph.
3. Every navigable list is either a `<select>` (uniform rows, native up/down and Enter, focused when it is the active widget) or a non-focusable `<scrollbox>` of `<box>` rows when rows need custom content such as graph lanes, ref badges, diff headers, or inline actions. In the custom case, the region frame owns focus, and navigation and selection are implemented by `useListCursor` and rendered as a highlighted row background plus a leading text marker, except the graph, whose lane prefix and selected fill identify the row without a marker. `useListCursor` implements `g`/`G` only where the keymap binds `nav.first` and `nav.last`; `tags`, `stashes`, and `worktrees` deliberately do not bind them.
4. Mouse focus uses OpenTUI `autoFocus`. Clicking a text input focuses it; clicking any other element focuses the nearest focusable ancestor, normally the region frame. Region and row mouse handlers must not call `focus()` directly; they select the row and dispatch, and native focus follows the click. Double click is detected by `useListCursor` (two clicks on the same row inside a threshold). Mouse never exposes an action that has no keybinding. OpenTUI starts a global text selection on any left-button down over selectable text and leaves it active after a click that never drags, so `Button`, `Checkbox`, `SectionHeader`, and `ListRow` build their click handler with `src/ui/useClickWithoutSelection.ts`, which clears that selection before the owning action runs. Text outside a clickable primitive stays selectable for copy, and the console's `useSelectionHandler` copy-on-select is unaffected because it runs on a drag release.
5. Diffs always use `<diff>` with `view="unified"`, `showLineNumbers`, `fg` mapped to the `text` token, theme-mapped `addedBg`, `removedBg`, `addedSignColor`, `removedSignColor`, and syntax highlighting through `filetype` derived from the file path plus the theme-owned `SyntaxStyle` from `useSyntaxStyle`. A filetype without a registered parser keeps the `text` color; the app never downloads a parser at runtime. Collapsed unchanged runs are computed in `@/domain/diff/diff.collapse.ts` before the diff string is passed in. Every string passed to `<diff>` must be a valid unified patch with recomputed hunk headers; truncation cuts at hunk boundaries. The unified view draws one line-number gutter. The mockup's two-gutter appearance is illustrative; v1 deliberately renders one gutter rather than adding a custom renderer.
6. A custom-row list mounts every row of its bounded loaded window inside a `<scrollbox>` with `viewportCulling`, so the native scrollbar and the scroll offset describe the whole loaded list instead of a hand-rolled mounted slice; `DiffPanel` and the commit graph follow the same rule. Only the graph's loaded page window is bounded, by the cursor paginator in `@/domain/graph/graph.paginate.ts`, so the graph never calculates a second window for rendering. Every graph body row keeps a stable renderable id: `graph-row:<rowId>` for the Pending Changes row and each commit row, and `graph-search-row:<oid>` for each search result row. The graph scrollbox keeps `scrollY` enabled, disables `scrollX` because every row is width-budgeted, reserves one explicit column for the vertical scrollbar, hides the horizontal scrollbar, and uses the same scrollbar track color as the diff panel. `useGraphReveal` reveals the selected graph row, or the selected search result, through the scrollbox's own `scrollChildIntoView` when the selection or its row position changes, and once more on the renderer's next frame after the body switches between graph and search so that reveal sees settled row layout. A reveal skips any row whose layout has not been published yet (`height <= 0`), so stale geometry cannot scroll the viewport to the top. For the graph body, it reveals on a viewport-height change only when the selected row was visible before the change, so a growing footer cannot clip the cursor without pulling a freely scrolled viewport back; the search body keeps the target and frame reveals because it has no status footer, and it never reveals on a content resize inside one body, so appending a page leaves the user's scroll position alone. Mouse wheel and trackpad input scroll the native viewport and never move the selection, matching the diff and sidebar lists; the reveal runs on selection and cursor moves. Because a free scroll can leave the cursor outside the viewport, an up or down move re-anchors to the nearest visible edge instead of revealing the stale row, and a page move starts from that same anchor, so neither pulls the viewport back to where the cursor used to be. The last loaded row is followed by a `Load older commits` button when `canLoadOlder` is true, and the same read is bound to the key-only `graph.loadOlder` action (`L`), so history is never paged automatically by scrolling or by moving the cursor near the end. `canLoadOlder` is false while history is exhausted, a page is loading, a graph-window reload is in flight, a page error is unresolved, search owns the surface, or no rows are loaded; the button, the action handler, and the footer availability all read that one predicate. The graph scrollbox carries one cell of horizontal padding on each side, so its row budget subtracts that padding from the measured viewport width and a row never reaches the panel border or the scrollbar. The graph uses lazygit's two-cell lane model: the engine returns per-cell edge geometry, `GraphLanes` maps it onto the glyph set selected by `config.graph.style`, and a rounded fork reads as `◎─╮` while a join reads as `○─╯`. The `sharp` style swaps the arc corners for the WGL4 and CP437 safe corners, uses full line ends, and draws merges with an ASCII `+`. Every lane is one glyph plus one horizontal-connector cell. Each row starts its text immediately after its own lane grid, so a branch row is indented by its lane count while a linear row starts after one lane, and every row's second line continues the lanes that are still live below the commit. That is how lazygit places the commit message, and it keeps the tree read as one connected shape.
7. The console drawer is app-owned UI (not the renderer's built-in console). It is a `<box>` docked above the footer containing a `<scrollbox>` of entry `<box>` rows, so it can show command, status, duration, and expandable output in the app style. The renderer console is used only for development logging.
8. Disabled controls are rendered with a `dim` token and a text reason, and remain visible. The command palette uses `<select>` options whose `description` carries the disabled reason.
9. Truncation uses `@/lib/text.ts` helpers with explicit budgets from the measured scrollbox viewport width (`useScrollViewportSize` for graph rows, `useScrollContentWidth` for diff and details rows); it never hides the current branch, the selection signal, or the primary action.
10. Progress bars use `<frame-buffer>` through the `ProgressBar` primitive only. The bar is one row high, `0` to `100` percent clamped, drawn as colored cells with no glyphs, and always paired with a text phase and percentage. Redraw only when the filled cell count, width, a terminal resize, or the theme color changes, and redraw after a height-only resize because the resize clears the buffer. When no percentage is known the bar is not rendered at all; the status strip shows the spinner instead.
11. The startup splash is the only place `<ascii-font>` is used besides the empty-repository, non-repository, and terminal-too-small states. It renders the `GITMINAL` wordmark with `font="tiny"` above 40 columns and 10 rows and falls back to plain bold text below that, so the splash never wraps.

### 6.1 Icon catalog and rules

All icons, markers, and glyphs live in exactly one file: `src/theme/icons.ts`. It exports a frozen `ICONS` object and the `IconName` type, and it is the single place to configure the visual vocabulary of the app. The file sits in the theme folder so the icon layer and the color layer are configured together.

Rules:

1. Single source. `src/theme/icons.ts` is the only place a reusable icon or marker value is defined. Components import `ICONS` from `@/theme/icons` and never inline a reusable marker. The glyph check in section 12 fails on non-ASCII and box-drawing characters outside this file; printable ASCII UI text is allowed, and intent is enforced by review.
2. Single cell, single line, and two documented non-ASCII groups. Every value is printable ASCII except the sanctioned pictographs and the commit graph set. The pictographs are `push`, `pull`, and `tagUnpushed` (the upward and downward arrows), `expanded` (the downward triangle), `collapsed` (the rightward triangle), and `success` (the check mark). The arrows and the expanded triangle are in WGL4 and CP437; the collapsed triangle and the check mark are present in Consolas, Menlo, DejaVu Sans Mono, JetBrains Mono, and the other mainstream monospace fonts. `tagUnpushed` reuses the upward arrow because it is the same act as pushing. The commit graph set is `graphCommit` (`○`), `graphMerge` (`◎`), `graphMergeSharp` (`+`), and the box-drawing line and corner values from U+2500 to U+257F that `GraphLanes` maps the cell edges onto. The effective `config.graph.style` selects either the rounded arc subset (`╭`, `╮`, `╰`, `╯`, the half-lines, and `◎`) or the sharp subset (`┌`, `┐`, `└`, `┘`, full line ends, and `+`). The plain lines and tees (`│`, `─`, `┬`, `┴`) are in both WGL4 and CP437, but the arc corners (`╭`, `╮`, `╰`, `╯`), the half-lines (`╵`, `╷`, `╶`), and `◎` are not; they are present in Menlo, DejaVu Sans Mono, JetBrains Mono, Consolas, and the other mainstream coding fonts, while a WGL4-only or CP437-only font such as Monaco runs out of coverage and the terminal falls back to another font. Every value in both groups is East Asian Ambiguous, and OpenTUI's `unicode` and `wcwidth` width methods both measure it as one cell, which is what lets one graph lane occupy two cells without changing a row budget. A terminal configured to render ambiguous characters as two cells breaks that assumption and is the graph's known portability cost; there is no ASCII fallback mode in v1 because the sanctioned graph is the lazygit cell model. Every other value stays ASCII: no other arrows, no emoji, and no Nerd Font glyphs. The only terminals that cannot draw a non-ASCII value are ones with no UTF-8 path at all, such as a serial console, a non-UTF-8 locale, or a legacy Windows console on a Western codepage or a raster font; there the glyph degrades to a replacement box, which is acceptable because every use is paired with the words Pull, Push, up to date, exit 0, ahead/behind, an adjacent expandable title, or the commit text beside the graph. Review rejects any further non-ASCII value.
3. Never the only signal. Every icon that conveys state is rendered next to, or has, a text equivalent. Color is never the only signal either. For example the missing-upstream icon `[?]` is always shown with the words "upstream not found" or "remote branch deleted". This pairing is a design and review rule, not a machine-checked test, because the text equivalent is written where the icon is used. The remote local-tracker marker `[L]` is a documented notation meaning "a local branch tracks this exact remote branch", fixed by the RemoteRow JSDoc and tests rather than an adjacent word pair. The tag scope indicator is another documented notation instead of a word pair: its first slot states local presence with `L`, its second slot states the remote fact with `R`, `↑`, `?`, or a blank, and the letters are their own text equivalent. Its mapping is fixed here, in the Tags feature JSDoc, and in `src/features/tags/TagRow.test.tsx`.
4. Plain data, no hook. `ICONS` is a static module, so both UI and non-UI code can read it. It is not resolved through React. Because it lives in the theme folder, a future user-override layer can be added in `ThemeProvider` without changing consumers.
5. User overrides are deferred. v1 centralizes icons in the file but does not read them from user configuration. Making them user-configurable would extend `theme.json` with an optional `icons` object and requires a change to this section.
6. One-line values. Multi-character markers such as `[?]`, `[ ]`, and `[x]` are still single-line strings rendered inside `<text>` or `<span>`. Icons never introduce layout.

## 7. UI primitive catalog

`src/ui/**` holds the only reusable presentational components. Each is a composition of the OpenTUI catalog above.

| Primitive | OpenTUI composition | Purpose |
| --- | --- | --- |

Marker and separator widths are reserved before branch-name truncation. Search rows come from the same repository selectors as their sidebars and are not limited by sidebar render caps. Custom `ListRow` results keep the shared selection styling and a single-line name where it fits; long names wrap in the selected-item details. Search owns transient query and highlight only, leaving the sidebar cursor unchanged until Enter closes and requests a post-focus-restore reveal. The owning feature extends its render cap to include that identity, selects through its cursor without activation, and scrolls the selected row into view. Each acceptance carries a distinct one-shot reveal independent of cursor changes, so accepting the same freely scrolled-out row repeatedly still reveals it without interfering with ordinary free scrolling. Both sidebar acceptance and modal mount/highlight changes reveal only rows with published geometry and schedule a cancellable next-frame correction; target changes and unmount remove pending frame callbacks. Escape closes immediately and restores the captured sidebar focus and unchanged selection, even with a non-empty query. Up/Down (and paging/Home/End through search input routing) move only the overlay highlight. Loading, empty, no-match, and read failures are consistent across all four regions and retain live repository updates.


## 8. Focus and keybinding architecture

Regions (stable IDs in `src/features/shell/regions.ts`):

```text
top-bar, branches, remotes, tags, stashes, worktrees, graph, right-pane, diff, console
```

Direct region jumps use the digits `1`-`9` in screen order: `1`-`5` are the five sidebar panels, `6` is `graph`, `7` is `right-pane`, `8` is `diff`, and `9` is `console`. `top-bar` has no default digit but keeps a `focus.region.topBar` action for configuration and the palette. `regions.ts` owns the region IDs and their `focus.region.*` action IDs, `keymap.defaults.ts` binds the digits, `useFocusModel` registers the handlers, and a jump calls `focusRegion` instead of writing focus state. A jump to a sidebar panel that the collapsed layout is not showing selects it in the `<tab-select>` first. Digits resolve in the global context, so native list widgets do not consume them, but an overlay or a focused text input owns them through precedence rules 1 and 2.

- OpenTUI native focus is the authority. `renderer.currentFocusedRenderable` decides which renderable receives keys.
- `FocusProvider` subscribes to `renderer` events `focused_renderable` and `focused_editor`. It derives `activeRegion` from the focused renderable's nearest ancestor region frame (`region-<regionId>`), derives `textInputFocused` from `currentFocusedEditor !== null`, and derives `nativeListFocused` from the focused renderable being a `SelectRenderable` or `TabSelectRenderable`. If focus is outside every region, such as in an overlay, `activeRegion` keeps its last value while the overlay owns keys. It stores `previousRegion`, `focusedRenderableId`, `previousFocusedRenderableId`, and the per-region cursor map. It exposes `focusRegion(regionId)`, `focusRenderable(id)`, and `restoreFocus(id)`. It does not expose a writable `activeRegion` or a manual text-input flag.
- `useFocusRegion(regionId)` returns `{ focused, focus(), regionProps, getCursor, setCursor }`. `regionProps` sets a stable id `region-<regionId>`, `focusable`, and `focusedBorderColor` on the region frame. `focused` is true when the focused renderable is the region frame or a descendant, including a text input inside it. It is false while focus is in an overlay.
- `useFocusModel` owns Tab and Shift+Tab traversal in the spec order, the `focus.region.*` direct jumps, skips regions hidden by responsive fallbacks, appends the `console` region to the cycle only while the drawer is open, and calls `focusRegion(next)` instead of writing focus state directly.
- A text input or other widget that must be focused programmatically has a stable id and is focused with `focusRenderable(id)`. `focusRegion` is only for a region frame. Examples are `graph.search` focusing the search input and `commit.focus` focusing the composer textarea.
- Text input mode applies when `currentFocusedEditor` is not null. `Esc` leaves the input without clearing its value and normally returns focus to the owning region frame; a feature may consume the first `Esc` for a documented cancel or clear or define a different return target (the composer returns to the textarea's region), but the next `Esc` must leave the input. `Tab` and `Shift+Tab` follow the field type first: in a multiline `<textarea>`, `Tab` inserts the indent unit at the cursor and `Shift+Tab` removes up to one indent unit from the start of the current line, and neither moves focus, including inside an overlay; in a single-line `<input>`, they move to the next or previous region in the shell, or to the next or previous field or footer action inside an overlay. The textarea indent unit is `TEXT_INDENT_UNIT` (two spaces) in `src/lib/text.ts`, and replaces the selection when one exists. A textarea exposes `insertText` through its ref so the handler can insert the indent before calling `preventDefault()`.
- Input modes are part of keymap resolution, not exceptions handled ad hoc by features. Every focused editor resolves to one of three modes: `field` (plain single-line or multiline editing), `search` (a single-line search over a result list), or `form` (a modal or shell form with fields and footer actions). The mode is a pure function of the focused editor's registered `InputMode` metadata.
  - `field` owns every unmodified printable key, Backspace, Delete, arrows, Home, End, and Enter. A textarea's Enter inserts a newline; a single-line input's Enter invokes its native submit callback.
  - `search` keeps printable keys and editing keys in the field, but routes Up, Down, PageUp, PageDown, Home, and End to the bound result list, and routes Enter to `nav.activate` for the highlighted result. A search mode is declared by the owner when it registers the input.
  - `form` keeps printable keys and Enter in a single-line field, routes `Tab`/`Shift+Tab` between fields and footer actions, and maps `Ctrl/Cmd+Enter` to `form.submit`. A multiline form field keeps `Tab` for indentation and uses `Ctrl/Cmd+Enter` for `form.submit`.
- OpenTUI editing behavior is preserved. In text input mode, only an explicit text-input-safe allowlist of app actions may fire: `app.palette`, `app.console`, `commit.submit`, `commit.options`, and `form.submit`. Such an action fires only when its effective binding uses `Ctrl`, `Cmd`, or `Alt`; an unmodified default binding for the same action never fires while an editor is focused. This is why `commit.options` remains reachable as `Alt+.` in the composer while plain `.` types a period. Every other key, including every modified key not in that allowlist, passes to the input or textarea untouched. This preserves `Enter` submit on single-line inputs, `Enter` newline on textareas, and the OpenTUI editing bindings: `Ctrl+A/E/F/B/W`, `Ctrl+Backspace/Delete`, `Ctrl+K/U`, `Ctrl+-/.`, `Super+A/Z`, and `Alt+D/F/B` plus arrow variants. Configured app bindings outside the allowlist never fire while typing, even when they use a modified key. `Ctrl+C` remains the hardcoded app quit path defined in section 8 and is the one deliberate exception.
- `Ctrl`/`Cmd`-modified shortcuts do not resolve through the app keymap in text input mode. They do so only outside text input mode or when they are in the text-input-safe allowlist above and use a modifier. Unmodified keys always pass to the input.
- Native list mode applies when a `<select>` or `<tab-select>` is focused. That widget owns `nav.up`, `nav.down`, `nav.pageUp`, `nav.pageDown`, `nav.first`, `nav.last`, and `nav.activate`; `useHotkeys` must not prevent those keys from reaching it. A focused `<tab-select>` also consumes Left and Right natively, which is how the collapsed sidebar switches panels; no app action binds those keys in a sidebar context. A plain `<select>` does not bind Left or Right, so an overlay keeps its horizontal control rule while a select is focused. `useHotkeys` reads the focused widget and editor from the renderer at key time instead of the `FocusProvider` projection, because a focus move is applied synchronously by the renderer but reaches the projection on its next render; a key that arrives in the same input burst as the focus move would otherwise be routed by stale state. Global modified shortcuts, `focus.next`/`focus.previous`, and the `focus.region.*` digit jumps still work.
- `overlay` is not a region. On open, `OverlayProvider` captures the current focused renderable, blurs it, and focuses the first focusable element in the modal after mount. While open, the overlay owns keys. The overlay context applies the same text-input and native-list delegation for keys it does not handle; region focus does not apply. On close, it restores the captured renderable if it is still mounted, otherwise it focuses that renderable's region frame. `close(afterRestore)` accepts an optional completion that the provider runs from an effect declared after the restore effect, once the restore is acknowledged; the completion belongs to that one close session, runs at most once, is discarded instead of retained when another surface is open at that point, and must not throw.
- Outside a modal text field, the only global actions that may resolve while an overlay is open are the overlay's own toggle and `overlay.close`: `app.palette` when the palette is the open overlay, `app.help` when help is the open overlay, and `app.quit` as the hardcoded quit escape hatch. They toggle or close that overlay. No other global action, including `remote.*`, `app.themePicker`, or `app.reloadConfig`, is reachable until the overlay closes. Inside a modal text field, `overlay.close` on `Esc`, the hardcoded `Ctrl+C` quit path, and modifier-gated text-input-safe actions may also fire; a plain unmodified global action never does. An open modal may consume the first `Esc` through the focused-surface clear registry in `src/app/hooks/useInputEscapeClear.ts`, which the global `overlay.close` handler consults before it closes the overlay; help registers it while its search has text, so `Esc` clears and the next `Esc` closes. The console drawer is not an overlay; `app.console` stays global while it is open.
- The startup splash is not a region and has no focus. It renders before the providers and the keymap mount. `SplashGate` owns the only `useKeyboard` subscription while the splash is visible: `Ctrl+C` calls `onQuit` without dismissing, and every other key calls `onDismiss`. After dismissal `SplashGate` unmounts and the shell's `useHotkeys` owns keys, with `app.quit` as the quit path. `SplashGate` reads the fixed quit chord only through `src/app/quit.key.ts`.
- Only the `wsl` keymap platform adds `Ctrl+Space` to `app.console` alongside Ctrl/Mod+Backtick because Windows Terminal over WSL can encode Ctrl+Backtick as NUL, which OpenTUI reports as Ctrl+Space. Platform detection selects `wsl` only on Linux with a nonempty `WSL_DISTRO_NAME` or `WSL_INTEROP`; macOS, standalone Linux, and native Windows retain the catalogue defaults. The alias is an ordinary default binding, not an event rewrite: overrides replace it, plain backtick and space stay printable, and both control chords use the existing text-input-safe routing.
- Action IDs are defined in `src/domain/keymap/keymap.defaults.ts` and nowhere else. Features receive action IDs only.
- `KeymapContext` uses the exact `RegionId` values plus `global` and `overlay`: `top-bar`, `branches`, `remotes`, `tags`, `stashes`, `worktrees`, `graph`, `right-pane`, `diff`, and `console`. `useHotkeys` therefore looks up `contexts.get(activeRegion)` directly, with no adapter or cast between the focus model and the keymap.
- `nav.left` and `nav.right` bind the top bar, the right pane, and overlays, with `Left`/`h` and `Right`/`l` as defaults. Sidebar panels do not bind them: the collapsed switcher is a native `<tab-select>` and owns those keys in native list mode.
- Precedence is computed in `src/domain/keymap/keymap.resolve.ts`. A key may appear once per context. Context overrides global for the same key.
- `diff.stageAll` invoked through its diff-scoped shortcut (`S`) stages only the section that owns the cursor: Working Directory or Untracked Files. On Staged Files it is blocked as an invalid target. The global `diff.stageAllUnstaged` (`A`) stages the deduplicated union of Working Directory and Untracked Files paths independent of the selected row or section and sends explicit literal paths with no section. Inline section Stage All buttons retain their own section and path sets. Read-only, busy, conflict, and empty-path guards still apply to every stage-all path. Other bulk diff shortcuts retain their selected-section scope.
- Diff cursor recovery is feature-owned in `useDiffRows`: when a selected file disappears from the editable list, selection returns to that file's section header instead of falling onto an adjacent section. This keeps subsequent bulk shortcuts targeting the same section across staging, commits, and status refreshes. Surviving file identities retain the shared cursor behavior.
- The diff surface scrolls its own scrollbox vertically and horizontally through `useDiffScroll` and the `diff.scroll*` actions (`J`/`K`, `Shift+Down`/`Shift+Up`, `H`/`L`, and `Shift+Left`/`Shift+Right`). Those actions change viewport offsets only: they clamp at the scrollbox edges, never wrap, never move the cursor, and stay silent when there is nothing to scroll. `nav.up`/`nav.down` keep moving the row cursor, and `useScrollSelectedRow` keeps that row visible through the same scrollbox. The step sizes are feature constants in `diffPanel.constants.ts`, and the horizontal offset stays 0 until the user scrolls right; the selection reveal targets width-capped section headers and file rows, so it moves the viewport vertically only and keyboard row navigation never changes that horizontal offset. The horizontal scrollbar is hidden because OpenTUI draws it in the last row of the panel body at the bottom edge of the frame; `H`/`L` plus `Shift+Left`/`Shift+Right` are the supported keyboard horizontal controls, and Shift+wheel or a horizontal wheel can still move the offset when the terminal reports it. The vertical scrollbar stays visible, and it reserves one explicit column so a long diff line that widens the content cannot push it over the panel border. All six `diff.scroll*` actions are key-only: they have no command descriptor and no command palette entry. Installed `@opentui/core` 0.6.6 creates each diff code renderable with `width: "100%"` and `wrapMode: "none"`, so `scrollX` alone clips long diff lines instead of widening the scroll content. The deliberate deviation is that `DiffContent` sizes each `<diff>` through `readDiffContentWidth` in `diffContent.layout.ts`: the measured panel width while the longest rendered line fits, and the natural line width plus the exact line-number gutter once a line is longer. A scroll-only structure cannot reveal clipped content in this version, so this width pass is required rather than optional. Section headers, file rows, empty states, and notices stay at the measured width, so only diff content becomes horizontally scrollable.
- Footer hints come from `src/domain/keymap/keymap.describe.ts` filtered by the focused region and current availability. Help and the palette read the same effective keys and availability reasons, but they keep unavailable actions visible; only footer hints drop them. The `focus.region.*` actions are help- and palette-only and are never emitted as footer hints. Self-evident actions are suppressed everywhere, the More menu trigger stays visible so `.` is discoverable, and the `top-bar` context additionally suppresses `nav.activate`, `app.themePicker`, and `app.refresh`. The `branches` context passes `includeGlobals: false` to `describeFooterHints` and suppresses its own `nav.activate`, and every other content region also passes `includeGlobals: false`, so a focused block lists only its own verbs. The diff scroll hints are ranked first in `CONTEXT_HINT_PRIORITIES` so `J`/`K`/`H`/`L` survive width shrinking, while the fast `Shift+Down` and `Shift+Up` variants are filtered out by the footer. The `graph` context also suppresses the `nav.pageUp` and `nav.pageDown` hints because most laptop keyboards lack those keys. The top bar and the no-focus fallback keep the global hints. The focused control or row already shows what Enter does, and Help and the palette remain the discovery surfaces.

### 8.1 Action, command, and handler model

Action IDs and commands are related but distinct:

- An **action ID** is the stable, key-bindable intent, for example `app.quit`, `branch.delete`, `nav.activate`, or `focus.region.graph`. The catalogue in `src/domain/keymap/keymap.defaults.ts` is the only source of action IDs. Action IDs are the only names accepted in `config.json` and `keybindings.json`.
- A **command ID** is a stable, palette-invocable operation. Most commands reuse their action ID as the command ID. Internal commands such as `graph.selectCommit`, `stash.select`, and `worktree.select` are command IDs with no action ID and no default key. `nav.*` actions are key-only and are never palette commands. `focus.region.*` actions are key-bindable navigation commands and remain palette- and help-invocable because they are the discovery surface for direct region access.
- `src/domain/commands/commands.registry.ts` is the single catalogue. Each descriptor declares `id`, optional `actionId`, `kind` (`mutation`, `read`, or `navigation`), handler `scope` (`global`, a `RegionId`, or `overlay`), `targetKind`, label, description, keywords, category, `paletteInvocable`, and `needsInput`.

Targets are explicit values, not ambient cursors:

```ts
type CommandTarget =
  | { kind: "none" }
  | { kind: "branch"; name: string }
  | { kind: "remoteBranch"; remote: string; branch: string }
  | { kind: "tag"; name: string; remote?: string }
  | { kind: "stash"; objectName: string }
  | { kind: "worktree"; path: string }
  | { kind: "commit"; oid: string }
  | { kind: "pending" }
  | { kind: "diffFile"; section: DiffSection; path: string; oldPath?: string }
  | { kind: "form"; formId: string }
```

Two kinds of state feed a target. The right-pane selection union (`pending`, `commit`, `stash`, `worktree`, or a diff file) lives in `RepositoryProvider`. Per-region cursors live in `FocusProvider` keyed by stable identity. A command's owning feature derives its target from one of those sources through a selector, never from another feature's local component state.

Availability is target-aware:

```ts
type CommandContext = {
  state: RepositoryState
  signals: RepositorySignals
  target: CommandTarget
  region: RegionId | "overlay"
  operation: "idle" | "running"
}

getAvailability(commandId, context): { available: boolean; reason?: string }
```

`src/domain/repository/repository.states.ts` exposes `gateRepository(actionId, state, signals)` for repository-wide gates such as detached HEAD, empty repository, or missing remote. `src/domain/commands/commands.availability.ts` combines that result with target validation, so a branch action can explain "cannot delete the current branch" and a diff action can explain "read-only" from the same call. The footer, palette, help, buttons, and confirmations all read the same result.

Handlers are scoped and singular:

- `src/app/hooks/useAction.ts` exposes `useAction(actionId, { scope, targetKind }, handler)`. Exactly one handler may exist per `(actionId, scope)`. A duplicate registration is a development error and the later registration is rejected; last-mounted-wins is never allowed.
- Global actions (`app.*`, `focus.*`, `remote.*`, `diff.stageAllUnstaged`, `overlay.close`) have exactly one designated owner: `src/app`, the shell, the always-mounted top bar for the `remote.*` operations it presents, or the always-mounted diff panel for its global stage-all action. Features register only their region-scoped actions, such as `branch.delete`, `diff.stage`, or `nav.activate`. A panel that unmounts in the collapsed layout never owns a global handler; the diff panel stays mounted in `MainArea` in every layout, which is why it may own `diff.stageAllUnstaged`.
- `useHotkeys` resolves the focused scope first, then the one global registration. `nav.activate` is registered by the focused region only, so the active surface owns it.
- The palette captures `{ commandId, target }` when it opens from the selector above. On Enter it re-derives the same target and compares the two by value. If the fresh availability is false, the target is missing or differs from the capture, or the owning surface is hidden by the collapsed layout, the palette closes and shows the availability reason, and its post-restore completion focuses the owning region when that region's frame is mounted; when the owning panel is hidden by the collapsed layout, the restored focus stays where it was and the status strip carries the reason. Switching the collapsed sidebar panel remains a recorded deferral in the F-01 ownership row. It never dispatches to a hidden panel's stale cursor. Otherwise it dispatches to the owning scope handler. Handlers take no target argument: the handler re-derives the target from the same live projection, so the captured target's equality check is the safety boundary and the handler and the palette always read the same selector. A list-row handler re-reads its region cursor, so it assumes the cursor identity and the cursor index still name the same row after the post-restore dispatch; a background refresh that lands between validation and that dispatch is the residual risk, because it can rewrite the row list in that window. The scope-to-region mapping that turns a global command into an `overlay` availability question lives with the shared target derivation in `useCommandTargets.ts`, so the palette and help ask the same region.
- The palette closes through the overlay's `close(afterRestore)` operation, and the overlay provider runs that completion from an effect declared after the focus-restore effect. The ordering is causal rather than timed: the palette closes, the overlay restores the captured background focus, then the completion runs the owning handler, or the refusal's move to the owning region. The completion belongs to that one close session: once the restore is acknowledged it is cleared, and it is discarded instead of retained when another surface is open at that point, so it can never run on a later unrelated close. A command that opens another overlay can therefore render one committed frame of the restored background before the new overlay appears.
- Commands described by `needsInput` open an input surface owned by another component. The flag is descriptive: the owning handler performs the open, and the palette does not branch on it. Commands whose target is the right-pane selection read `RepositoryProvider.selection`; commands whose target is a list row read the focused region's cursor projection.

## 9. State architecture

The startup splash runs before any provider mounts. It owns only local view state and one background update check, then unmounts.

Providers, outermost to innermost:

1. `ConfigProvider`: resolved config, warnings, reload. Source: `@/domain/config`.
2. `ThemeProvider`: resolved tokens and color capability. Source: `@/domain/theme`. Exposes tokens through `@/theme/useTokens.ts`, the full resolved theme through `app/hooks/useTheme.ts`, and the renderer-bound syntax style through `@/theme/useSyntaxStyle.ts`.
3. `KeymapProvider`: resolved action to keys map. Source: `@/domain/keymap`.
4. `RepositoryProvider`: repository snapshot, the right-pane selection union (`pending`, `commit`, `stash`, `worktree`, or `diffFile`), and the refresh cycle. Source: `@/domain/repository` and `@/domain/git`. It does not own row expansion.
5. `DraftProvider`: the composer draft string and `hasUnsavedDraft`. The composer reads and writes this provider and does not duplicate the draft; the shell quit handler will read `hasUnsavedDraft` here once draft-based quit lands, and no feature imports another feature to answer the unsaved-work question. The footer reads the repository through `useOptionalRepository`, which returns null outside a provider so shell-only tests do not need the repository stack.
6. `FocusProvider`: a projection of OpenTUI native focus, `previousRegion`, and the per-region cursor map. It is not a second focus authority.
7. `OverlayProvider`: one open overlay entry at a time (a feature modal or a destructive/non-destructive confirmation) plus the focus captured when it opened. Opening a second entry replaces the first instead of stacking. The persistent error detail and the error overlay landed in M6. Success and informational messages are not overlays.
8. `StatusProvider`: transient status, footer hint mode, operation progress. It is the only surface for success and informational messages. Success and informational messages auto-dismiss after a short timeout; warning and error messages stay until another status replaces them or `clearStatus` removes them.
9. `ConsoleProvider`: drawer visibility, bounded command log, follow mode, new-entry count, expanded entry ids, and the pending cross-surface selection request (`pendingSelectionEntryId`).

Data flow for a mutation:

```text
key, click, or palette -> action ID or command ID + explicit CommandTarget
   -> useAction handler for the focused scope, or the single global handler
   -> useCommandRunner.runCommand(request)                              (app layer, the only caller)
   -> commands.runner.ts (availability + serialization + execution)     (domain, no providers)
        -> @/domain/git/* -> git CLI -> CommandResult and progress events
   -> useCommandRunner applies the result:
        StatusProvider progress and status   <- git.progress.ts
        ConsoleProvider entry                <- git.redact.ts -> console.format.ts
        RepositoryProvider.refresh()         on success and failure
        OverlayProvider error                on failure
   -> features re-render
```

Read refresh (manual `app.refresh`, watcher, and terminal focus) does not pass through the command runner: `app.refresh` -> `useAction` handler in `useRepository` -> `RepositoryProvider.refresh()` -> domain read modules.

Rules:

- Command execution is split. `src/domain/commands/commands.runner.ts` is a pure executor: it owns availability, write serialization, execution, and progress reporting through a callback, and it returns a `CommandResult`. It never imports React, a hook, a provider, or `src/app/**`. `src/app/hooks/useCommandRunner.ts` is the app-layer orchestrator and the only caller of the runner; it owns `RepositoryProvider.refresh()`, `StatusProvider` progress and status, `ConsoleProvider` append, and `OverlayProvider` errors. Features call the orchestrator, never the runner. `commands.registry.ts` marks every entry with `kind: "mutation" | "read"`; only mutations reach the runner, while reads such as `app.refresh` call `RepositoryProvider.refresh()` directly.
- State has exactly one owner: snapshot, selection union, and refresh generation in `RepositoryProvider`; composer draft in `DraftProvider`; cursors and previous region in `FocusProvider`; the single overlay entry and its captured focus in `OverlayProvider`; transient status and progress in `StatusProvider`; console entries, follow mode, and expanded entries in `ConsoleProvider`; config, keymap, and theme in their providers. Row expansion, focused control index, filter text, and modal form drafts are feature view state, owned by exactly one feature. `RepositoryProvider` never owns expansion, and a feature never keeps a second copy of the selection.
- The right-pane sub-mode is derived, not stored: `selection.kind === "pending"` renders the composer, `"commit"` renders commit details, `"stash"` renders stash details, `"worktree"` renders worktree details, and a diff-file selection leaves the current right-pane mode intact while the diff panel highlights the file. There is no separate sub-mode flag in a provider or a feature.
- Repository reads are derived in `@/domain/repository/repository.selectors.ts`. Features never recompute ahead/behind, upstream state, or pending counts themselves.
- Optional ref lists settle independently. A failed branch, remote-branch, tag, stash, or worktree read keeps that list's previous snapshot value and records the failure in `RepositoryProvider.listFailures` for the owning panel, while every successful list still applies. Status and the remote list are required reads: a failure there fails the whole read and the provider keeps the previous snapshot. A retained worktree or branch list re-derives the branch `worktreePath` values from the worktrees the snapshot stores, so the branch `+` marker, the selected-row worktree detail, and the `checked-out-in-worktree` delete guard stay consistent with the Worktrees rows that remain visible.
- Every command declares availability in `@/domain/commands/commands.availability.ts` with a machine-readable reason string and a target-aware context. The palette, footer, help, buttons, and confirmations all read the same reason.
- Read-only diff mode is derived, not caller-supplied. `isReadOnlySelection` in `repository.selectors.ts` is the single predicate over `RepositoryProvider.selection` (`commit` or `stash`); `useRepositoryAvailability`, `useCommandRunner`, and the diff feature all use it, the runner carries the flag into the handler context, and every diff executor refuses with `read-only` when it is true. The feature-owned form flag remains an additional defense, never the authority.
- Failures never clear drafts or staged files. The runner returns a result object; the orchestrator keeps the UI inputs and surfaces the error.

## 10. Git execution architecture

- `src/domain/git/git.client.ts` is the only module that spawns processes. It uses an argument array, `git.path` from config, `cwd` at the repository root, no shell, and stdin ignored.
- Captured output is bounded per stream. The collector keeps the first and last half of `outputLimitCharacters` (1,000,000 by default) and reports truncation only when a chunk no longer fits, so a complete capture under the limit is never treated as truncated. Because graph and search pages are bounded by commit count rather than by bytes, a page whose capture overflows is retried with a halved page size down to one commit before the read fails; the parent frontier and the search offset stay unchanged across retries.
- Credential and editor prompts are disabled through an explicit environment matrix. The client sets `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`, `GIT_ASKPASS=""`, `SSH_ASKPASS=""`, `SSH_ASKPASS_REQUIRE=never`, `GIT_EDITOR=true`, `GIT_SEQUENCE_EDITOR=true`, `GIT_PAGER=cat`, `PAGER=cat`, `GIT_MERGE_AUTOEDIT=no`, and `LC_ALL=C`. It sets `GIT_SSH_COMMAND=ssh -o BatchMode=yes` only when the user has not configured `GIT_SSH_COMMAND` or `core.sshCommand`; a user-configured SSH command wins. The `core.sshCommand` probe caches only a conclusive answer, and a cancelled, timed-out, spawn-failed, or generic git failure is retried instead of overriding a configured command. A missing credential or network failure fails visibly and is logged; the app never hangs on a prompt.
- Every invocation has a timeout and a cancellation signal. Defaults are 10 seconds for local reads, 30 seconds for local writes, and 120 seconds for network operations. `git.client.ts` accepts an `AbortSignal`; on abort it sends `SIGTERM`, waits two seconds, then sends `SIGKILL`, and returns a cancelled result. Timeouts use the same path and are reported as "timed out after N seconds". A terminated child settles on its `exit` event; a normal exit waits for `close` only during a bounded 100 ms flush grace, so a backgrounded descendant that inherits the output pipes cannot defeat the timeout or delay quit. Once a normal exit is recorded the invocation timeout is cleared, so a late timeout or abort cannot rewrite a completed command as timed out or cancelled. Quit aborts the in-flight command through the orchestrator, waits for it to settle, and destroys the renderer only after the child has exited or been killed. M4 deviation: draft-based quit confirmation remains deferred beyond the M6 overlay work, so `app.quit` always aborts immediately; the abort-before-destroy order is implemented.
- Writes are serialized inside `commands.runner.ts`. Index-touching reads (`status`, `diff`, `log --raw`) are serialized against writes by `git.client.ts`, so a status read never observes a half-applied mutation. A second write while one is running returns a blocked result with a reason. The runner holds no provider state; the blocked reason and the running flag are projected to the UI through the orchestrator and `StatusProvider`.
- `commands.runner.ts` executes only. It returns a `CommandResult` with the operation label, the ordered `steps` (each with argv, exit status, duration, stdout, and stderr), cwd, progress phases, and the cancelled or timed-out flag. A composite operation such as create-with-checkout, delete-local-and-remote, or a grouped prune records one step per git invocation so the console can show each command. A step marked `nonFatal` does not make the result a failure: the documented case is a scoped Fetch --prune whose configured upstream no longer exists on the remote, where the step stays in the console, the result stays a success, and `warnings` names the affected branch so the orchestrator shows a warning status instead of the error surface. A non-fatal step also never marks the command timed out: the timeout flag stays on its `CommandStepResult`, the console step entry keeps the exit status, and the reason travels through `warnings`, which is what lets the remote-wide prune fail or time out without relabeling the fetch that already succeeded. The console row derives its exit label from the last step that reported an exit code, skipping a trailing non-fatal step that reported none, so a trailing non-fatal timed-out step cannot render an unknown exit on a successful row, while a fatal step without an exit code reports no row exit code instead of borrowing an earlier step's `0`. A handler that refuses its scope before working returns `blockedReason`, which the runner turns into a blocked result with no steps. A handler that contacts remotes may also return `remoteResults`, a per-remote success list; `useRemoteCommands` records `RepositoryProvider.recordRemoteCheck(remote, "fetch", succeeded)` for each entry, so a completed fetch advances that remote's last successful fetch timestamp and a failed remote leaves it untouched. A Fetch --prune handler also returns `prunedUpstreamRefs` and `unknownUpstreamRefs`; the wrapper folds both lists into repository evidence and performs one refresh before returning, so the orchestrator's own refresh sees the new upstream classification without one full read per ref. A Fetch --prune group also runs one `git remote prune -- <remote>` invocation for a remote whose check and scoped fetch both finished cleanly, so a stale tracking ref that no local branch tracks is removed too. The prune runs on the network class while the per-ref `git update-ref -d` deletes run on the write class, and it runs first: `git update-ref -d` on an already-absent ref is a clean no-op, so the prune-first order cannot fail a delete the prune already performed, and a failed explicit delete really keeps its ref locally instead of losing it to a prune that would have followed. A cancelled prune skips the explicit deletes for that group, while a cancellation still stops the run. A failed or timed-out prune is a warning and leaves the group's result and its freshness evidence unchanged. The prune is skipped under the `current` fetch scope, because it deletes tracking refs of the whole remote while the evidence lists report only in-scope refs; the `local` scope covers every local branch upstream, so only there do the remote-wide prune and its evidence agree. A run whose every remote group failed and that fetched or pruned nothing sets `failed: true`, so a total failure reaches the error surface while a partial failure stays a success with warnings. The runner never refreshes the repository, appends a console entry, sets a status, or opens an overlay. `src/app/hooks/useCommandRunner.ts` applies those effects after the result.
- Ordinary Fetch (`remote.fetch`, `f`) always fetches origin's configured refspecs with `git fetch --progress --no-prune --no-prune-tags -- origin`, independently of local upstreams and `config.remote.fetchScope`. The palette expands Fetch into one entry per existing configured remote (including upstream when configured), captures the exact remote name, revalidates availability, and sends the same command with an explicit `remote` form value through `useCommandRunner`. An absent origin blocks `f` with `unknown-remote`; it never silently chooses another remote. The executor reads `git remote` again before contacting the remote, then reads `remote.<name>.fetch` and refuses destinations that can write local heads (including unqualified destinations and mirror `refs/*` overlap) with the actionable `unsafe-fetch-refspec` reason. An unreadable or truncated configuration fails closed. This deliberate exception to custom-refspec semantics protects the approved no-local-branch-changes guarantee; ordinary remote-tracking refspecs retain git semantics. Explicit no-prune flags override git's pruning configuration. Fetch does not check out, create, or delete a local branch. Successful and failed fetches use the orchestrator's repository refresh, which updates remote branches and causes the graph's ref-tip reload when refs change.
- `config.remote.fetchScope` remains accepted with its existing `local` default and `current` alternative, but now governs only the distinct Fetch --prune operation. Its scoped fetch phase runs one invocation per upstream ref with `git fetch --progress -- <remote> +refs/heads/<branch>:refs/remotes/<remote>/<branch>`. The forced-update prefix mirrors remote rewrites without targeting a local branch. `local` reads every local branch upstream and blocks with `no-local-upstreams` when none exist; `current` requires the exact checked-out branch's upstream and blocks with `no-current-upstream` otherwise. `commands.fetch.scope.ts` owns the prune request and planner logic; availability carries the same scope and current-upstream flag. The tab-separated `%(refname:short)%09%(upstream:remotename)%09%(upstream:remoteref)` atoms preserve exact remote names, including names containing `/`.

- Network operations pass `--progress` (`git fetch --progress`, `git pull --progress --no-edit`, `git push --progress`) and stream stderr through `git.progress.ts`; the runner forwards progress events to the orchestrator, which updates `StatusProvider`. Commands without a meaningful percentage emit phase-only events, and a phase-only event for a new phase clears the previous percentage. Remote and ref arguments are validated as single safe argv values and passed after `--` where git supports it; `git update-ref` places `--` after `-d`, and `git remote prune` places `--` before the remote. Push plans always name the configured upstream remote and an explicit `refs/heads/<branch>:refs/heads/<upstream.branch>` refspec after reading `git branch --show-current`, and the no-upstream path uses `--set-upstream origin refs/heads/<branch>:refs/heads/<branch>`, so `push.default=matching` cannot widen the scope and a stale snapshot cannot push the wrong branch. The configured upstream itself is read with `%(upstream:remotename)` and `%(upstream:remoteref)`, never by splitting `%(upstream:short)`, because a legal remote name may contain a slash; Fetch and Fetch --prune use the same atoms.
- `git.redact.ts` redacts credentials in URLs, authorization headers, and environment values before any console or error rendering. The orchestrator applies redaction to the `CommandResult` before it stores or renders output.
- `git.watcher.ts` watches the git directory and triggers refresh. Recursive watching is requested first; when the platform refuses it, the git directory and its ref directories are watched non-recursively and the limitation is published through the watcher status. Worktree watching is opt-in and off by default, filters a documented ignore set, and reports its own limitation. Because the default git-dir mode leaves the working tree unwatched, F-17 assigns a text hint to the footer or sidebar surface. The M5 top-bar status strip is reserved for branch information, operation progress, and transient status, and no component renders the hint yet; the deferral is recorded in the F-17 ownership row in section 15 so this contract does not claim a surface that does not exist. `.git/index.lock` churn never triggers a refresh, and a watch error closes the watch and publishes an inactive status. Manual `r` refresh is always available.
- Parsers under `src/domain/git/parsers/` are pure and unit tested against recorded git output fixtures. Process-spawning integration tests live in `*.integration.test.ts` files and use `src/test/git.fixture.ts` to create and remove temporary repositories.

The executor contract lives in `src/domain/commands/commands.types.ts`:

```ts
type CommandRequest = {
  commandId: string
  target: CommandTarget
  formValues?: Readonly<Record<string, string | boolean | readonly string[]>>
}
type CommandProgress = { phase: string; percent?: number }

type CommandStepResult = {
  argv: readonly string[]
  exitCode: number | null
  durationMs: number
  stdout: string
  stderr: string
  cancelled?: boolean
  timedOut?: boolean
  timedOutAfterMs?: number | null
  stdoutTruncated?: boolean
  stderrTruncated?: boolean
  nonFatal?: boolean
}

type CommandResult = {
  commandId: string
  status: "success" | "failure" | "blocked"
  operationLabel: string
  steps: readonly CommandStepResult[]
  cwd: string
  progress: readonly CommandProgress[]
  blockedReason?: string
  warnings?: readonly string[]
  cancelled?: boolean
  timedOut?: boolean
  timedOutAfterMs?: number | null
}

type CommandRunOptions = {
  state: RepositoryState
  signals: RepositorySignals
  target: CommandTarget
  region: RegionId | "overlay"
  signal?: AbortSignal
  onProgress?: (progress: CommandProgress) => void
}
```

`commands.runner.ts` exposes one entry point: `runCommand(request, options): Promise<CommandResult>`. It returns a failure result instead of throwing for a git failure, and a blocked result for an unavailable command, a missing target, or a rejected second write. `state`, `signals`, `target`, and `region` are plain values from `RepositoryProvider` and `FocusProvider`; the runner calls the pure `commands.availability.ts` itself. Provider data crosses the boundary as data, never as a hook or context. Only `src/app/hooks/useCommandRunner.ts` calls the runner in application code; tests call it directly.

`useCommandRunner` exposes `runCommand(request): Promise<CommandResult>` and applies the result in this order:

1. Capture the current `RepositoryState`, `RepositorySignals`, explicit `CommandTarget`, and region, then compute availability with `commands.availability.ts`. If the command is unavailable or the target is missing or stale, surface the reason as a transient status and return a blocked result without starting an operation, refreshing, or appending.
2. `StatusProvider.beginOperation` before invoking the runner.
3. Invoke `commands.runner.ts` with the captured values and an `AbortSignal` owned by `useCommandRunner`. The runner re-checks availability and serialization as the authority; if it returns a blocked result, call `endOperation`, surface the reason, and skip refresh, console, and error effects.
4. `StatusProvider.updateOperation` for each progress event.
5. `git.redact.ts` on every step's stdout, stderr, and argv, plus cwd, followed by the pure control-character sanitizer in `console.sanitize.ts`; argv, cwd, and warnings use its single-line mode, while stdout, stderr, and error messages keep newlines and tabs.
6. `console.format.ts` then `useConsoleLog` to append exactly one entry.
7. `RepositoryProvider.refresh()` after success and failure. A cancelled or timed-out result refreshes so the UI reflects any partial local change.
8. `StatusProvider.endOperation` plus a success or warning status, or `OverlayProvider.showError` on failure. A cancelled result sets a warning status "cancelled"; a timed-out result sets "timed out after N seconds" when the client reported the duration. Neither opens the error overlay. A requested mutation returns `operation-in-progress` before `beginOperation` while an orchestration still owns the post-result refresh, console, and status effects.

A settled result closes only the overlay entry that was open when the command started, through `OverlayProvider.closeEntry(entryId)`. An unrelated confirmation opened while the command runs, or a visible error detail, is left untouched. A caught exception is redacted and sanitized before it reaches the error detail, and it appends exactly one console entry that the overlay links to. When the exception follows an already-appended result entry, for example a rejected post-result refresh, that entry is replaced in place with a failure carrying the same summary, and the overlay reports the distinct operation `Refresh after <command>`, so the title, linked entry status, and summary agree. A thrown entry summary and decisive error are single-line, while the overlay message keeps newlines; both thrown and settled detail blocks are capped with the shared console rule. The retry closure consumes a rejected re-run because the error detail is already stored, so an unhandled rejection cannot terminate the TUI.

A read path (`app.refresh`, watcher, focus refresh) never enters this flow. It calls `RepositoryProvider.refresh()` directly.

M4 deviations, recorded here per the last rule in this document:

- The error overlay landed in M6. `useCommandRunner` routes settled failures to `OverlayProvider.showError` with redacted, sanitized details, the console entry link, and a retry closure for retryable remote commands; Retry re-runs the original request, including its form values.
- Draft-based quit confirmation remains deferred beyond M6. `app.quit` aborts the in-flight command and waits for it to settle before `renderer.destroy()`; it does not yet ask about `DraftProvider.hasUnsavedDraft`.
- M4 wired the first real mutation through the orchestrator: `remote.fetch` executes named-remote `git fetch --progress --no-prune --no-prune-tags` on the network class. M5 adds `remote.pull`, `remote.push`, `remote.pushForceSafe`, `remote.pushForceOverwrite`, `remote.pushNoVerify`, and `remote.fetchPrune` through the same registry, runner, and orchestrator path; the M5 top bar replaces the temporary trigger, not the path. Only Fetch --prune is blocked with `no-local-upstreams` when the repository read resolves no local upstream, and a configured upstream whose remote ref is gone is a non-fatal warning that names the branch rather than a command failure. Pull requires a configured upstream, plain push and push --no-verify auto-create `origin/<branch>` when none exists, and the force variants require an existing upstream. Fetch --prune confirms remote absence with `git ls-remote --heads -- <remote>` before any `git update-ref -d`, and a failed, timed-out, or truncated check leaves its refs unknown instead of deleted. After a clean check and fetch it runs `git remote prune -- <remote>` before the explicit deletes, so every stale tracking ref of that remote is removed, including one that no local branch tracks; the prune itself is remote-wide because git defines it per remote, while `fetchScope` still decides which remotes are touched, and git's own refspec comparison keeps a tracking ref whose source namespace such as `refs/pull/<n>/head` still exists. The prune runs only for the `local` scope, because a `current`-scoped run cannot report the refs a remote-wide prune would remove. A failed prune is a warning, a timed-out prune is the warning `${remote}: prune timed out; stale refs kept`, and neither fails the group. Push and its variants read the current branch from git, fail on a mismatch with the captured target, and use an explicit configured-upstream remote and `refs/heads/<branch>:refs/heads/<upstream.branch>` refspec. The configured upstream remote and branch come from `%(upstream:remotename)` and `%(upstream:remoteref)`, and Fetch --prune groups the same atoms by the exact remote name, so a slash-named remote is never split. The prune orchestration and scope policy live in `commands.prune.ts`, the git phase primitives (check, fetch, delete, prune) in `commands.prune.phases.ts`, and the accumulator, outcome, and summary helpers in `commands.prune.outcome.ts`, all over the type-only contract in `commands.prune.types.ts`. The network invocation helper in `commands.invoke.ts` is shared by the fetch, prune, pull, and push executors, and the synthetic step helpers in `commands.steps.ts` are shared by the fetch, prune, and push executors, because pull has no plan to reject. The extraction is done, not deferred. `commands.remote.ts` (288 lines) and `commands.prune.phases.ts` (291 lines) sit inside the 250-300 line review band, `commands.prune.outcome.ts` (196 lines) is below it, and `commands.prune.ts` (342 lines) is the only module above it. Each module is single-responsibility. That size is accepted because the split follows the executor's real seams instead of a line count, and splitting the orchestration further would spread one contract across more files than it is worth. The remaining outstanding extraction target is `commands.remote.push.ts` for the push and upstream readers, when a fourth composite remote command lands or before the v1 freeze.
- Repository reads expose an explicit `failureKind`. Cancelled, timed-out, auth-network, and unknown failures keep the previous snapshot and record a redacted `lastRefreshError`; only a genuine not-a-repository classification produces `not-a-repository`, and only a genuine missing-git or permission failure produces those environment states.

## 11. Configuration and theme architecture

- `@/domain/config/config.paths.ts` resolves `config.json`, `keybindings.json`, and `theme.json` using the documented configuration precedence.
- Load order is defaults, `config.json`, `keybindings.json`, then runtime reload. The bootstrap loads the three files before the first render through `src/app/providers/config.source.ts`, so the shell has no loading state, and `ConfigProvider` keeps the resolved snapshot: effective config, resolved paths, per-file load status, validated `keybindings.json` overrides, the raw `theme.json` layer, and bounded warnings. Each file read is capped at 256 KB, and an oversized file produces one bounded warning instead of being buffered. `config.writer.ts` creates the configuration directory recursively and replaces `config.json` through a sibling temp file plus a rename, removing the temp file on failure. Validation is per field; an invalid field falls back to the previous effective value and produces a warning. `src/app/hooks/useConfigActions.ts` is the single owner of the global `app.reloadConfig` action: a reload re-reads and re-validates through the same source, applies in place on success, and keeps the previous effective configuration on a rejected file. Configuration warnings surface as a non-blocking top-bar status and one console notice, never an overlay. `combineConfigurationWarnings` in `@/domain/config/config.warnings.ts` merges the configuration warnings with the theme resolution warnings behind a `Theme:` prefix and bounds them once, so the top bar, the console, and Help report the same deduplicated set. `src/app/hooks/useMouseSetting.ts` assigns `renderer.useMouse` from `config.ui.mouse`, and the bootstrap passes the startup value to `createCliRenderer`, so a reload changes mouse reporting without a restart. `config.graph.style` selects the commit graph glyph set at render time: `rounded` keeps lazygit's arc corners and bullseye merge symbol, while `sharp` uses the WGL4 and CP437 safe sharp corners, full line ends, and an ASCII `+` merge symbol for fonts whose box-drawing coverage is partial.
- `@/domain/theme/theme.catppuccin.ts` is the only place hex colors exist. It defines the four flavors and the token table from F-20.
- `@/domain/theme/theme.capability.ts` detects truecolor, 256-color, and monochrome, and honors `NO_COLOR`; `theme.capability.palette.ts` owns the xterm-256 nearest-color search. Token resolution returns final colors per capability, and `ThemeProvider` memoizes the truecolor resolution and the capability mapping separately.
- Every production scrollbox uses `src/ui/useScrollbarOptions.ts` for both axes: thumb and arrow foregrounds use `scrollbar`, and track and arrow backgrounds use `background`. This shared hook updates with theme previews, restores, and terminal capability mapping; individual surfaces retain ownership of scrollbar dimensions and visibility. This is a review rule, with live theme-switch coverage in `ScrollableList.test.tsx`.
- UI reads colors only through `useTokens()`. No component holds a hex literal. `Swatch` is the only UI primitive that paints a caller-supplied color, and it falls back to the `ICONS.swatch` marker when the capability has no color.
- Syntax highlighting reuses the same token table. `src/theme/syntax.constants.ts` maps base tree-sitter capture scopes onto existing tokens, keeping green and red reserved for added and removed diff lines, and `src/theme/syntax.styles.ts` turns the resolved tokens into OpenTUI style definitions. `ThemeProvider` creates one renderer-bound `SyntaxStyle` per token set, destroys the previous one, and exposes it through `useSyntaxStyle()`; `DiffContent` passes it with `pathToFiletype(path)` to every `<diff>`, and commit details uses the same instance, so a theme switch or capability downgrade repaints both. OpenTUI bundles JavaScript, TypeScript, TSX, Markdown, and Zig parsers, and the ten vendored grammars add Bash, CSS, Go, HTML, Java, JSON, PHP, Python, Rust, and YAML; any other filetype renders in the `text` token with no download attempt.
- Grammar assets are shipped, not fetched. `bun run parsers:vendor` copies one wasm and one `highlights.scm` from each pinned grammar package into `assets/parsers`, writes `NOTICE.md` with the package, version, license, and source of every grammar, and fails when the combined wasm payload exceeds 6 MB. `src/app/syntax.parsers.ts` turns those files into OpenTUI registrations with absolute paths derived from the asset directory, `src/index.tsx` registers them before the first render because the tree-sitter client reads the parser set once, and `src/test/treeSitter.load.ts` registers the same set for tests through `bunfig.toml`. `package.json` publishes `assets` next to `dist`, so the same relative asset URL resolves from `src/` and from `dist/`. Injections are not registered because the worker cannot honor `injection.language` metadata, so embedded languages inside HTML and PHP stay uncolored, and a parser that fails to load degrades to plain text instead of blocking the diff.
- The sidebar `ListRow` selected fill uses `surface` as a deliberate exception to the generic selected-row `selection` token; native selects and focused buttons still use `selection`. `THEME_TOKEN_TARGETS` and product F-20 record the exception. `BranchRow` and `RemoteRow` additionally suppress the `ListRow` selection marker because the one-cell current or worktree marker and the dark fill, or the dark fill alone, already identify the row. `TagRow`, `WorktreeRow`, and `StashRow` suppress it for the dark fill alone and keep a one-cell indent, so their rows retain the same one-cell sidebar inset. The graph rows use the same `surface` fill and suppress the selection marker so the lane prefix starts at the leading edge, matching the mockup.
- `@/theme/icons.ts` is the single configuration file for every icon, marker, and glyph. No component inlines a glyph. Icons are single-line, single-cell values, printable ASCII apart from the documented pictographs (push, pull, tag-unpushed, expanded, collapsed, and success) and the commit graph symbols and box-drawing lines, and always have a text equivalent; the pairing is enforced by review, not by a module test. See section 6.1.
- The theme picker previews by swapping tokens in `ThemeProvider` without writing the file; Enter persists through `config.writer.ts`. `ThemeProvider` exposes `preview(name)`, `commit(name)`, and `restore(previous)` as session-only controls read through `useThemeControls()`, and `src/app/hooks/useThemePickerAction.tsx` is the single owner of the global `app.themePicker` action that opens it as an `OverlayModalEntry`. The picker registers only overlay-scoped handlers, and a failed write keeps the theme for the session with the documented warning.

## 12. Enforcement

These rules are checked, not aspirational. Enforcement lands in slices, not all at once:

1. Slice 1 enables typecheck, Biome, unit tests, and all three enforcement scripts: `scripts/check-boundary.ts`, `scripts/check-glyph.ts`, and `scripts/check-structure.ts`. The structure check runs in warning mode for folders that are planned but not yet created.
2. Each later slice adds the checks for the code it introduces and turns the structure warning for its own folders into an error.
3. The v1 freeze runs `bun run check:structure --strict`, which asserts the full tree in section 4 and the complete feature ownership map in section 15.

Package commands:

- `bun run check` runs `biome check .`, then `check:boundary`, `check:glyph`, and `check:structure`.
- `bun run check:all` runs `bun run check`, `bun run typecheck`, `bun run test`, and `bun run test:integration`.
- `bun run check:fix` stays the Biome autofix only.
- `bun run check:boundary`, `bun run check:glyph`, and `bun run check:structure` run the TypeScript checkers directly through Bun. `bun run check:structure --strict` promotes planned path warnings to errors.

Rules:

- TypeScript strict mode is already on. Keep `noUncheckedIndexedAccess` and `noImplicitOverride`. `resolveJsonModule` is on for `app.constants.ts`.
- `bun run typecheck` must pass before any change is considered done.
- Biome handles linting, formatting, and import organization. `bun run check` (or `bun run check:fix` to apply safe fixes) must pass before any change is considered done. Configuration lives in `biome.json`; Markdown formatting is disabled there because its tables are hand-aligned. The `src/ui/**` override turns off `a11y/noStaticElementInteractions`, because OpenTUI boxes are the only layout and hit-test primitive and have no DOM role; a UI primitive never repeats that rule as a per-file suppression comment.
- Husky manages Git hooks. The pre-commit hook runs `fallow audit` against the merge base with the branch upstream and blocks commits that introduce error-severity findings (dead code, complexity, duplication, or styling). Configuration lives in `.fallowrc.jsonc`; the `.fallow/` cache is git-ignored. `bun run audit` runs the same analysis manually. Function-size and complexity review uses fallow's findings, not a hand-written line-count parser. Because fallow counts every React hook call toward a hook's cognitive complexity against the documented ceiling, a surface with more than a dozen concerns splits into one hook per concern - view state, catalogue, operations, and key registrations - instead of one hook that registers every action. The `scripts/**` enforcement checkers use the default health ceilings and have colocated unit tests, so no `health.thresholdOverrides` entry is needed.
- `bun test` runs the unit suite and must pass. `bun test:integration` runs `*.integration.test.ts` against temporary repositories created by `src/test/git.fixture.ts`. Both must pass before publishing, and `bun run check:all` runs both, so the real-git proofs for planners such as `git remote prune -- <remote>` sit inside the enforced gate instead of beside it. Unit tests never spawn a process; integration tests may spawn the system git only through the fixture.
- `scripts/check-boundary.ts` (`bun run check:boundary`) walks every `.ts`, `.tsx`, `.js`, and `.jsx` file under `src/` with the TypeScript AST and fails on:
  - any external package import under `src/domain/**` or `src/lib/**`; React and `@opentui/*` are included, so domain and lib stay free of runtime packages. Any Node builtin under domain or lib outside the per-module allowlist in section 3 is rejected the same way.
  - any local import under `src/domain/**` outside `src/domain/**` and `src/lib/**`.
  - any local import under `src/lib/**` outside `src/lib/**`.
  - any external package or builtin import under `src/ui/**` other than React and `@opentui/*`; any local import under `src/ui/**` outside `src/ui/**`, `src/lib/**`, and `src/theme/**`. UI may import only React, `@opentui/*`, `src/ui/**` primitives, `src/lib/**`, and `src/theme/**`.
  - any external package or builtin import under `src/theme/**` other than React and `@opentui/*`; any local import outside `src/theme/**`, `src/domain/theme/**`, and `src/lib/**`. Theme may import any module under `src/domain/theme/**`, using token types type-only as the review norm. It never imports UI, features, app, or another domain folder.
  - any import of a test-only module from a production module. The test-only imports are the test runners `bun:test` and `node:test`, plus `src/test` and any module under `src/test/**`. A colocated `*.test.*` file and a module already under `src/test/` may import both a test runner and a module under `src/test/**`. The domain, lib, ui, theme, and feature rules reject all of them with their own layer message; the app layer and `src/index.tsx` are otherwise unconstrained, so this guard is the one edge they cannot cross.
  - any external package or builtin import under `src/features/**` other than React and `@opentui/*`; any local import outside `src/ui/**`, `src/domain/**`, `src/lib/**`, `src/theme/**`, and the same feature folder; any `src/app/**` import other than `src/app/hooks/**` and provider hooks under `src/app/providers/**` (a file whose basename starts with `use`). `src/app/App.tsx`, `src/app/AppShellHost.tsx`, and other app modules are never allowed from a feature.
  - feature to feature imports (covered by the same rule). `src/app/AppShellHost.tsx` is the composition root and is exempt because the app layer may import everything except the test-only imports, `bun:test`, `node:test`, and `src/test/**`.
  - process spawning through a `node:child_process` or `child_process` import, or a `Bun.spawn`, `Bun.spawnSync`, `Bun.shell`, or `Bun.$` call or tagged template outside `src/domain/git/git.client.ts` and `src/test/git.fixture.ts`.
  - network access through a `node:http`, `node:https`, `node:http2`, `node:net`, `node:dgram`, `node:tls`, or `undici` import; a `fetch`, `Bun.fetch`, `globalThis.fetch`, or `window.fetch` call; a `Bun.connect` call; or a `WebSocket` construction outside `src/domain/update/update.check.ts`.
  - raw key string comparisons: an equality operator (`===`, `==`, `!==`, `!=`) between a string literal and a key-like `name`, `sequence`, `raw`, or `code` property access outside `src/domain/keymap/**`, `src/app/hooks/useHotkeys.ts`, and `src/app/quit.key.ts`. A receiver named `key` or ending in `Key` is key-like for every key field. A receiver named `e`, `ev`, `event`, or ending in `Event` is key-like only in a key-aware file, so outside a key-aware file a plain `catch (e) { e.code === "ENOENT" }` and a non-key-aware `event.code` are not flagged. `name` and `sequence` follow the same receiver rule. A bare `name`, `sequence`, `raw`, or `code` identifier is flagged only in a file that mentions `KeyEvent`, `useKeyboard`, or `key.name`/`key.sequence`. Ordinary data fields such as `error.code` and `branch.name` are not key fields. Two known limitations are deliberate heuristics to revisit when the keymap layer adds type-aware checks: in a key-aware file a `catch` binding named `e` is treated as a key receiver, so `catch (e) { e.code === "ENOENT" }` is a known false positive; and the checker inspects only equality comparisons and property access, so element access such as `key["name"] === "c"` and `switch (key.name)` are known false negatives.
  - hex color literals outside `src/domain/theme/theme.catppuccin.ts`.
  - `index.ts`, `index.tsx`, `index.js`, and `index.jsx` barrel files other than the bootstrap `src/index.tsx`.
  - files named `utils`, `helpers`, `common`, or `misc`.
  - top-level functions, class methods, and exported arrow functions without a JSDoc block, checked with the TypeScript AST. Colocated `*.test.*` files are exempt. Function body size is not machine-checked; fallow owns complexity and size findings for production files. Test files are exempt from the split guidance but are still reported by fallow as review signals.
  - `bun:test` and `node:test` imports are allowed in colocated `*.test.*` files and modules under `src/test/`; these imports are test-only and rejected from every production module. Colocated test files and `src/test/**` modules may also import the shared fixture under `src/test/**`; every other external and local import still follows the layer rule.
- `scripts/check-glyph.ts` (`bun run check:glyph`) walks string, template, and JSX text literals in every `.ts`, `.tsx`, `.js`, and `.jsx` file under `src/` with the TypeScript AST and fails on non-ASCII codepoints outside `src/theme/icons.ts`. It deliberately allows printable ASCII punctuation and letters such as `>`, `v`, `M`, `[?]`, and `|`; those are UI text in many places and cannot be distinguished mechanically from icon values. Icon intent is enforced by review and by the rule that all reusable markers come from `ICONS`. The catalog is the only exempt file, so the six pictograph values and the commit graph set stay legal there while any other non-ASCII literal under `src/` still fails.
- `scripts/check-structure.ts` (`bun run check:structure`) reads `ARCHITECTURE.md`: the section 4 tree and the section 15 feature ownership map. It fails when an implemented source file under `src/` or `scripts/`, including a `.js` or `.jsx` file, is absent from the section 4 tree, or when an implemented feature folder has no section 15 ownership entry. Colocated `*.test.*` files are excluded from the unlisted-file scan. If the architecture document is missing or unreadable, or the section 4 or section 15 heading, fence, or table cannot be parsed, it reports a file diagnostic against `ARCHITECTURE.md` instead of throwing. It warns for planned paths that do not exist yet; `--strict` promotes those warnings to errors for the v1 freeze. It compresses a missing planned folder to one warning instead of one per planned file.
- Review checklist for every change: layer direction respected, action IDs and command targets used instead of raw keys, exactly one handler per action and scope, tokens used instead of colors, icons used from `@/theme/icons` instead of inline reusable glyphs, JSDoc present on every production function and method (test files are exempt), oversized production functions split (test files are exempt from the split guidance), states covered, tests added for domain logic, region frames focusable with stable ids, and no application code writes `activeRegion` directly or calls `focus()` from a mouse handler.

## 13. Testing strategy

- Domain: pure unit tests with recorded git fixtures. No spawning in unit tests.
- Integration: `*.integration.test.ts` uses `src/test/git.fixture.ts` to create a temporary repository, configure a local identity, seed commits, run the real git commands through `git.client.ts`, and remove the directory. Colocated test files may import `@/test/git.fixture`; production modules must not, and external package rules still apply inside tests. Fixtures cover prompting hooks, merge and rebase conflicts, empty and bare repositories, index lock files, and fixture-owned cleanup. They are skipped when `git --version` is below the supported minimum, Git >= 2.31.0, which is also the fixture floor. The graph and diff integration suites run the real `--diff-merges=first-parent`, search, stats, commit-diff, and size-probe invocations, so the floor is measured rather than claimed. `src/domain/git/git.availability.integration.test.ts` is the one unskipped guard: it asserts `isGitAvailable()` is true, so `bun run test:integration` fails on a machine without git >= 2.31 instead of silently skipping every fixture suite.
- Keymap and config: table-driven tests for precedence, conflicts, `null` reset, `[]` unbind, and per-field fallback.
- Commands: availability matrix tests covering detached HEAD, no upstream, no remote, empty repository, operation in progress, missing target, and stale target. `commands.runner.test.ts` asserts pure execution, write serialization, the blocked result, progress events, and cancellation. `useCommandRunner.test.tsx` asserts exactly one repository refresh, one console append, and one status transition per result, plus error routing and draft preservation on failure.
- UI: component tests with `@opentui/react` test-utils and `test-utils.ts` to assert rendered text markers, footer hints, and focus transitions.
- Focus: `FocusProvider` derives the region from native focus; a focused text input keeps its region active; `useHotkeys` does not consume unmodified typing keys; region frames are focusable and use `focusedBorderColor`; overlay open and close restores the previous renderable. Handler registration tests assert that duplicate `(actionId, scope)` registrations are rejected and that palette targets are explicit.
- Performance: fixture with a large synthetic log to assert page bounds, one in-flight page load, stale-result discard, and window-preserving refresh.

## 14. Change documentation policy

This file is the only architecture and behavior contract. There are no separate feature documents, tickets, or specification files.

- Every change that adds, removes, or moves a file, folder, component, provider, hook, command, state owner, or enforced rule updates this document in the same change.
- Feature behavior is documented by the feature's JSDoc, its constants, and its tests. Tests are the executable behavior contract; a behavior that matters and is not covered by a test is not protected.
- A rule that this file states but no script or test enforces is a review rule. State that explicitly instead of implying automation.
- When a rule must change, change the rule here and the enforcing script or test together, and record the reason in the commit message.

## 16. How to add a feature or file

1. Add or update the feature's row in section 15 with its owned paths.
2. Add the feature folder under `src/features/<name>/` with the exact files listed in section 4, or update section 4 if the structure changes.
3. Add domain modules under `src/domain/**` if new git or pure logic is needed.
4. Add any new icon to `src/theme/icons.ts` rather than inlining a glyph, and give it a text equivalent.
5. Add JSDoc to every new function, method, and component, and split any function that exceeds the size rule in section 5.1.
6. Add tests next to the code and cover the behavior the feature exists for.
7. Run the boundary and structure checks, `bun run typecheck`, and `bun test`.

Any change that breaks a rule in this document must update this document in the same change with the reason.
